## The transparency problem is solved

**Resolved 2026-09-23.** `logo-transparent.png` was supplied with a real alpha channel -
verified: 4 channels, `hasAlpha=true`, and all four corner pixels read alpha 0. It is the
source for the header mark and the favicon set, and it can sit on any surface.

`Logo.png` remains in the directory and is **not** the file to use. It is 1254x1254 PNG
colour type 2 - truecolour, no alpha - so it renders as a solid square on anything but its
own near-black field. Nothing references it any more except this table.

Two properties of the replacement worth knowing:

- **It is pixel art.** Every render sets `image-rendering: pixelated`, and `npm run brand`
  resamples it nearest-neighbour. A smooth kernel turns crisp square pixels to mush - the
  same reason `02-assets/sourcing.md` downsizes the 16x16 item textures that way.
- **It is 392x383, not square, and small.** Ample for a 32px header mark and a favicon
  set. It is *not* large enough to upscale into a hero or a dedicated Open Graph image, so
  the banner fills that role instead.

## File sizes, resolved

`npm run brand` (`scripts/compress-brand.js`) produces the served derivatives with `sharp`,
which was already a dependency:

- Banner **2,278 KB PNG to 258 KB WebP** at full width, with `srcset` at 768 / 1280 / 1672
  so a 375px phone downloads 85 KB rather than all of it.
- Logo 186 KB to **16 KB** WebP, alpha preserved.
- Favicons at 32, 180 and 512 as indexed PNGs - 2, 14 and 47 KB. Truecolour encodes put
  `icon-512` at 232 KB; the mark has few colours, so a palette encode is a fifth of it.

`icon-512` is **larger than the 392px source, so the art is not scaled up** - it is placed
1:1 on a padded transparent canvas. A 1.306x non-integer enlargement is precisely the mush
nearest-neighbour exists to avoid, and app icons want padding anyway. Sizes below the
source are resampled nearest-neighbour, which shrinking tolerates far better. The
threshold is read from the source file at run time, so supplying a larger transparent
export automatically changes which sizes pad and which resample.

The PNG originals stay in the repository and are never served.

## Do not background-key `Logo.png`

Recorded because it is the obvious next idea and it is wrong. `Logo.png` has no alpha, so
keying its flat near-black field looks like a way to get a 1254px transparent mark for
free. Measured: **81.4%** of `Logo.png` sits within 6 of its corner colour, while the real
background in the transparent export is only **46.3%** of the image. The dragon is itself
charcoal, so a colour key would punch holes through the subject, not merely fringe its
edges.

If a higher-resolution mark is ever wanted, it has to come from a fresh export of the
original artwork with alpha - not from keying this file, and not from a background-removal
service, which would also mean uploading the artwork to a third party for a job that has a
correct local answer.

## Aspect ratios

The banner is roughly 16:9 (1.78:1), so it drops into a standard hero slot without
cropping and doubles as the Open Graph image. The mark is near-square, which suits a
header mark and a favicon without a separate crop.

## Palette

**Superseded by ADR 0010.** The table that stood here was extracted from `Logo.png` by
`npm run palette` and is kept in `ground-truth/reports/brand-palette.md` as the record of
how it was derived. It is no longer what the site renders.

The palette now comes from the design kit, `design/tokens.css`, copied to
`apps/web/src/styles/tokens.css` - still the only file in the application that defines a
colour, and still a rule that re-eyedropping inside a component breaks.

Two themes, not one. Light is the `:root` default, dark applies under
`prefers-color-scheme` unless `data-theme="light"` overrides it, and `data-theme="dark"`
forces it. The toggle writes that attribute and persists the choice in `localStorage`.

Contrast is measured, not asserted: `npm run contrast` (`scripts/check-contrast.js`) reads
the token file and recomputes WCAG 2.1 for every pair the application actually renders,
writing `ground-truth/reports/token-contrast.md`. **38 pairs across both themes, 0
failing.** It exits non-zero on any failure, so a token edit that breaks contrast is loud.

Load-bearing values, light theme, from that report:

| Pair | Measured | Carries |
|---|---|---|
| `--text` on `--bg` | 15.63:1 | body text |
| `--muted` on `--bg` | 7.00:1 | secondary text |
| `--faint` on `--surface` | 5.59:1 | raw tokens in mono |
| `--link` on `--bg` | 5.88:1 | inline links |
| `--cta-text` on `--cta` | 11.83:1 | the Discord button label |

The kit states its own ratios on `design/artboards/tokens-board.html`. They were recomputed
rather than transcribed, and they agree.

Each of the five spawn buckets has its own glyph as well as its own colour, so the buckets
are distinguishable without colour at all. `ultra-rare` keeps the prominence
`01-data/server-notes.md` requires - it is a Bakumon-specific tier above rare, not a
footnote to it - and the kit gives it a double frame rather than borrowing the rare red.

## Typography

**Superseded by ADR 0010, and the display face again by ADR 0011.** ADR 0009 declined
webfonts, and that decision was sound for a site with no design system. The kit supplies
one, so three faces are now loaded - and **self-hosted**, never from Google Fonts:

| Face | Role | Weights |
|---|---|---|
| Baloo 2 | display: headings, labels, chips | 400-800 variable |
| Atkinson Hyperlegible | body: all prose and UI | 400, 700, 400 italic |
| IBM Plex Mono | identifiers | 400, 500 |

The kit's display face was Pixelify Sans. ADR 0011 replaced it with Baloo 2 - same role,
same self-hosting terms, rounded rather than pixelated.

Latin subset only, six woff2 files in `apps/web/public/fonts/`, **115,808 bytes total**,
declared in `apps/web/src/styles/fonts.css` with `font-display: swap`. All three are OFL.

Self-hosting is not a preference. A Google Fonts request is a third-party request on every
page load, which ADR 0007 rules out and which would falsify the privacy page's claim that
nothing is collected. `grep -rn "fonts.googleapis\|fonts.gstatic"` over `apps/web/src`,
`index.html` and the built `dist/` returns nothing, and that grep is part of the launch
check rather than a one-off.

ADR 0009's reason for a mono face survives the change intact: `cobblemon:ability_capsule`,
`#cobblemon:is_overworld`, `snake_pattern=attack`, species slugs and the raw `%s Poke Puff`
are code and must look like code. Rendering them proportionally is how they get read as
prose.

**One place still falls back to a system sans**: the tagline on the Open Graph share card,
`npm run sharecard`. sharp resolves SVG fonts through the system font stack and the kit
faces are woff2, which is not installed. The wordmark image carries the display face as
artwork, so the card still reads correctly. Recorded here rather than left as a silent
substitution.

The wordmark is now an image, `assets/brand/wordmark.png`, not text - the kit supplies one
and the alpha-channel reason for setting it as text no longer applies.
