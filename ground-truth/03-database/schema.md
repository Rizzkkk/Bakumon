# Schema

Defined by the migrations in `apps/api/src/db/migrations/`. This file explains **why** it
differs from `ground-truth/00-project/architecture.md` section 2, which it supersedes.

## Tables

| Table | Rows | Purpose |
|---|---|---|
| `pokemon` | 904 | One row per species |
| `pokemon_spawns` | 3,268 | One row per spawn entry, carrying form aspects |
| `items` | 934 | 932 from `Item Wiki` plus 2 backfilled |
| `biome_tokens` | 112 | Closed list powering the biome filter |
| `schema_migrations` | 1 | Migration ledger |

## Differences from the architecture doc

### `pokemon` is keyed on species, not on the spawn selector

`architecture.md` maps one sheet row to one `pokemon` row, keyed on column B. Column B is
a spawn selector carrying form aspects, so that would produce 1,107 Pokemon including
seven Arboks, and no form row would resolve to a PokeAPI image. ADR 0003.

Column added: `national_dex_id`, which exists solely to drive the PokeAPI image lookup.

### `pokemon_spawns` gained `aspects`, `selector` and `form_label`

The original schema had nowhere to put `snake_pattern=attack`, so 207 rows' worth of form
information was being discarded. `aspects` is `JSONB` so it stays queryable.

`bucket` holds five values and `context` six; the doc's comments say three and two. Both
are left unconstrained rather than `CHECK`ed, because a future server rebalance adding a
tier should not fail the import.

`level_min` and `level_max` are nullable - the six legendary event rows have `Level =
Event`.

`parse_flag` records which fields had to be padded. 2,302 of 3,268 rows carry one; see
`01-data/pokemon-spawns.md`.

### `items` has two category columns, and a count where a boolean was

`category` is the 4-value canonical axis; `source_category` is the 13-value axis where
berries, fossils and Poke Balls actually live. ADR 0002.

`used_in_evolutions BOOLEAN` became `evolution_use_count INTEGER` - the column holds
counts up to 10, and a boolean flattens them.

`wiki_description` is separate from `description` so the miner can never overwrite the
workbook. ADR 0004.

### `biome_tokens` is new

Most spawns reference a `#cobblemon:` tag rather than a concrete biome. A free-text biome
filter would match almost nothing. This table gives the UI a closed list of the 112 tokens
that actually appear, with a spawn count for each.

## Indexes

Beyond the GIN search-vector indexes the doc specifies:

- `pokemon_spawns_bucket_idx` - bucket is the primary browse filter.
- `pokemon_spawns_biomes_idx`, **GIN on the array**. The biome filter is an array
  containment query; a btree index cannot serve it.

Both were added on reasoning. They have now been **measured** - see
`ground-truth/reports/query-plans.md`, generated by `npm run explain` against the real API
queries - and the two came out differently:

| Index | Used? | Evidence |
|---|---|---|
| `pokemon_spawns_biomes_idx` | **yes** | `Bitmap Index Scan on pokemon_spawns_biomes_idx`, `Index Cond: (biomes @> '{#cobblemon:is_overworld}'::text[])`. Whole query 2.1 ms. |
| `pokemon_spawns_bucket_idx` | **no** | The planner prefers `Seq Scan on pokemon_spawns` with `Filter: (bucket = 'common'::text)`, 1,860 rows removed. Whole query 2.7 ms. |

The bucket index is **kept anyway, deliberately**. At 3,268 rows a sequential scan of the
whole table costs 0.76 ms and no index can beat that; the planner is right to ignore it.
It is retained so the query shape is already correct if the spawn table grows by an order
of magnitude, and because dropping it would mean a new migration for no measurable gain.
This is a decision to revisit only if the table stays small and the index shows up as
write overhead.

The page query itself is the one worth re-checking after any change: the summary lateral
must report `loops` equal to the page size, not to the match count. It currently reads
`Aggregate ... loops=24` and `Index Scan using pokemon_spawns_pokemon_idx ... loops=24`
against a 24-row page, with `Sort Method: top-N heapsort  Memory: 28kB` - in memory, so
no index on `(display_name, id)` is warranted either.

**Run `EXPLAIN ANALYZE` against the real API queries before adding any further index.**
`npm run explain` regenerates the whole report from the API's own query builders.

## Triggers

`search_vector` is maintained by trigger on both tables, and `updated_at` is set in the
same function. The items vector covers `name`, `description` **and** `wiki_description`,
so an item whose only description came from the wiki is still findable.
